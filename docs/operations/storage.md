# Durable SQLite 存储

Piko 使用 Durable 原生 SQLite 保存会话、消息、提交、任务和文档。应用只使用这一套持久化来源，不在 SQLite 之外维护第二份消息正文或执行状态。

## 存储位置与边界

- 数据库固定为 `PIKO_HOME/state/durable/session.sqlite`，默认 PIKO_HOME 为 `~/.piko`。
- SQLite 使用 WAL；运行期间可能同时存在 `-wal` 和 `-shm` 文件。一个状态目录只允许一个后端进程写入。
- 数据库损坏、目录中包含不受支持的旧格式，或非空目录缺少预期数据库时，后端拒绝启动，不会静默创建空会话或切换存储。
- 服务端运行日志独立写入 `PIKO_HOME/logs/`，不是 SQLite 内容或会话状态，详见[运行日志](logging.md)。
- SQLite schema v2 在 Durable 1.4.0 引入；pi-durable 1.5.0 仍使用 schema v2，没有新增 SQL 表结构迁移。1.5 会通过 Durable 原生版本化文档迁移更新旧 `pi.live` 文档（例如 compaction `reason` → `trigger` 与 `run.turns`），无需手工 SQL 转换。schema v2 不能由 Durable 1.3.0 或更早版本打开；1.5 写入的新文档值也不保证能由 1.4 回读。升级前必须备份整个 PIKO_HOME，并把升级视为不可直接回滚的持久化格式变更。
- 当前没有旧格式导入工具。需要从空白状态开始时，请使用新的 PIKO_HOME；不要直接覆盖或删除现有数据目录。

## 备份与恢复

1. 停止后端，并确认没有其他进程使用同一 PIKO_HOME。
2. 完整备份 PIKO_HOME，以及单独指定的工作区。会话可能包含用户消息、工具输入输出和文件路径，应按敏感数据保护。
3. SQLite 目录成套保存；不要只复制 `session.sqlite` 主文件而遗漏 WAL/SHM。
4. 恢复时使用同一工作区绝对路径；已有会话关联的工作区路径不匹配时，后端会拒绝启动。
5. 定期验证备份可恢复。备份本身不会随应用内删除操作一同清除。

## 删除与隐私边界

有明确业务归属的执行数据随所属对象删除：旁聊删除覆盖其后台工作；保存任务删除覆盖历次执行及专属任务目录；帖子删除覆盖正式正文及其专属生成过程。主会话已接收的报告与后续答复不随后台执行回收。旁聊和帖子删除不删除附件、记忆文件、工作区产物、外部备份或供应商侧记录，也不回滚外部副作用。具体边界见[旁聊](../features/side-chats.md#永久删除边界)、[任务](../features/tasks.md#持久化与目录)和[帖子](../features/posts.md#删除)。

SQLite 的 secure-delete、checkpoint 或 VACUUM 不能保证擦除文件系统快照、SSD 历史块、复制件或备份中的数据。不要将应用内删除描述为对所有介质的安全擦除。

## 临时执行的保留期

- 每隔 24 小时扫描一次，TTL 固定为 7 天。首次启用从当前时间开始计时，不立即清库；上次扫描时间保存在原生 `piko.storage-retention` session 文档，重启不重置。停机错过扫描时，恢复后补一次，不补跑多轮；扫描失败一小时后重试。
- 自动回收范围是主会话下无独立长期业务归属的普通委派、记忆整理，以及没有产出帖子的生成任务（跳过、失败、取消等）。保存任务执行、仍存在旁聊下的委派及已发布帖子的生成过程随所属对象保留，不套通用 TTL；不把任意未知或 ownerless conversation 当垃圾删除。
- 按整个执行归属树的最新原生终结时间、模型消息时间及显式停止活动计算保留期；任一关联任务未终结、时间无法确认、仍有排队/处理中输入、待父会话消费的报告或树外 fork/活动依赖时跳过。继续使用会产生新执行并重新计时。仍被记忆整理游标文档标记为活动的任务不清理。
- 不要求主会话空闲，不为回收停止模型或工具；逐个执行树提交并让出运行机会。过期后台 ID 不再支持查看或继续；父会话历史、记忆文件、保存任务定义和已发布帖子保留。
- TTL 删除释放 SQLite 内部页面供后续写入复用，不逐条 checkpoint/VACUUM，也不承诺主文件立即变小。用户主动永久删除仍执行 checkpoint、VACUUM、再次 checkpoint，失败不报成功。

## 共用删除协议

`server/runtime/storage-maintenance.ts` 共用所有权遍历、安全检查、文档退休、SQL 物理删除与恢复；各业务仅选择删除起点和额外回执。后台 Anchor/Reporter 是父会话中的关联节点，不能只按子会话内的 task 删除。

计划与退休在同一 Harness mutation line 上复核后提交；`piko.storage-deletion` 仅暂存待删会话、任务、文档和单项应用 entry 的 ID，不保存正文或执行状态副本。退休后禁止继续或停止目标，避免重新创建文档；物理删除事务完成后清空意图。中断后在 scheduler resume 之前完成，ID/commit 序号不回退。旁聊与保存任务仍保留各自的业务删除意图（包括输入关闭、任务定义和目录收尾）。Posts 删除后重建 root 的原生观察与历史投影，避免已删除应用 entry 留在阅读缓存中；不停止主会话。

隔离 SQLite/faux 模型已验证 7 天边界、24 小时扫描与重启计时、运行/新活动/待报告/fork/未知类型保护、归属删除、并发继续/停止保护、各类删除中断恢复及完整性。Web 独立浏览器覆盖桌面与 390px 帖子菜单、确认、取消、失败重试、忙碌锁定和产物阅读器回归；原生设备行为仍需真机验证。
