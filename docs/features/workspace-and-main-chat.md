# 工作区与主会话模型

状态：准备实施；本文件是下一阶段方案，不代表现有能力。遵循 [产品约定](../PRODUCT.md) 和 [架构约定](../ARCHITECTURE.md)。

## 目标与范围

用户始终回到同一个主会话。后端为助理提供独立于源码的长期工作区，保存聊天历史和执行记录，并能恢复模型对话上下文。此次不改聊天布局，不增加会话切换界面。

首个增量包含工作区初始化、资源加载、Workspace / Thread / Message / Run / RunEvent 契约、本地 SQLite 存储和重启处理。后续文件工具、技能创建/执行、记忆自动提取、Activity、后台任务均不在此增量。

## 工作区与资源

- 建议默认使用 `~/.piko/workspace`；允许显式配置绝对路径。具体配置名在实现时确定并更新 README，不把未实现的变量当可用命令。
- 状态库位于工作区外的 Piko 状态目录；Pi 模型与凭据先沿用现有 profile，Piko 资源加载独立管理。
- 首次初始化生成工作区标识与数据库记录、必要目录及简短指导模板。存在的文件保留；文件类型冲突、无权限、路径不可用应返回明确错误。
- 复用 Pi 加载器，显式加载用户 `.agents/skills` 和应用内建技能；关闭默认全局技能、扩展和祖先指导发现。同名用户技能优先，冲突可诊断。
- Piko 组装内建指导、工作区指导和运行上下文；SOUL / USER / MEMORY 有明确大小限制和加载范围。记忆正文与聊天历史不能全量无界注入。
- 本增量提供技能发现与诊断；没有受限读取工具时，不宣称模型已经能够按需使用完整技能。技能正文读取与脚本执行在下一增量接入。
- 主会话运行目录设置为助手工作区，不再使用 `process.cwd()` 对应的源码目录。不把 cwd 当作文件隔离边界。

## 领域与存储约束

首个增量只落地 Workspace、Thread、Message、Run、RunEvent。Thread 预留 `main | side` 类型及关联主会话的关系；side 不提供创建接口或 UI。

- 一个 Workspace 只有一个主 Thread，并发初始化也必须返回同一条记录。
- Message 有稳定 ID、Thread 归属、角色、内容和顺序；重启不根据 Pi 消息下标重建 ID。
- Run 关联 Thread、输入消息、输出消息与事件；重试记录旧 Run 关系。同一 Run ID 的同内容提交复用，内容不同时拒绝。
- 用户消息和 Run 的提交记录事务性写入后才启动模型；事件写入成功后再发布，快照和游标必须一致。
- 首期仍只允许一个 Thread 同时有一个活跃 Run。数据库事务或约束承担并发控制，不能仅靠 React 状态。
- 流输出按有限频率保存检查点，终态强制写入最终结果；记录可能丢失的最后一段输出边界。事件保留与回放窗口需要明确规则。
- SQLite 需要 schema 版本和迁移机制；首期单后端进程，多端客户端共享服务端主 Thread。

## API 与客户端迁移

目前客户端自行保存 `sessionId`，服务端按它创建内存会话。改为启动时向服务端解析默认 Workspace 与主 Thread，多端拿到同一主会话，再加载消息和 Run 快照。

现有聊天提交、快照、事件续订和取消语义继续保留。具体路径与 DTO 在实现契约时定稿；迁移需要说明旧 `sessionId` 的兼容或失效处理，不能将任意客户端 UUID 自动当成主 Thread。

实现时明确：旧浏览器缓存如何清理、运行中的旧协议客户端如何提示升级、旧内存历史是否做一次性导入。现有版本没有持久化历史，不能承诺恢复之前已经因重启丢失的内容。

## Pi 上下文与重启恢复

Piko 数据库是业务历史来源；Pi 持久会话保存模型上下文、摘要和运行时记录，两者通过稳定映射关联。不能仅保存可见文本后声称完整恢复了 Pi 上下文，也不能仅保存 Pi session 后丢失业务身份和 Run。

优先复用 Pi 的 SessionManager 和上下文压缩；实施前核对当前 SDK 的持久化、恢复及异常行为，确定 Pi session 文件位置、数据库关联和写入顺序。压缩不得删除用户可见消息。

重启时将遗留活跃 Run 标为明确的中断终态，保留已经持久化的部分输出，不自动再次调用模型。是否使用新 `interrupted` 状态或 `failed + errorCode`，在共享契约定稿时统一。用户主动重试产生新 Run。

SQLite 提交与 Pi 文件写入不构成单一事务。启动时应检查映射和检查点，明确如何修复缺失或落后的运行时记录；无法恢复时报告问题，不能默默开始空上下文聊天或重复执行。

## 实施顺序

1. 核对 Pi 持久会话与资源加载 API，定稿配置、实体、状态和接口，补充文档中的待定项。
2. 实现工作区解析、幂等初始化、SQLite 迁移及唯一主 Thread。
3. 接入有限范围的指导、技能索引和内建资源，继续保持扩展和通用工具关闭。
4. 将 Message / Run / RunEvent 接入存储，保持提交去重、快照、停止和重连行为。
5. 接入 Pi 会话恢复与长对话压缩，处理启动时中断和两套存储的一致性。
6. 客户端改为服务端主会话发现；验证多端一致和已有 UI 不回退。

## 验收

- 并发首次打开、刷新、不同客户端连接都得到同一工作区和主会话。
- 应用重开、服务端正常重启后消息 ID、顺序、内容和终态保留；继续发送时模型仍理解已有上下文。
- 创建模板不覆盖用户文件，重新初始化不创建第二个主会话。
- 不加载源码或祖先目录的指导、个人全局技能和扩展；内建/用户技能冲突遵循确定的优先级。
- 重复提交不重复写用户消息或调用模型；同 ID 不同内容、同 Thread 并发提交被拒绝。
- 断线恢复、停止与完成竞争、游标过期、模型失败均有明确结果。
- 运行中强制重启后显示中断与已保存输出，不自动重发；主动重试关联原 Run。
- 工作区无权限、数据库迁移失败、Pi session 缺失或损坏不会静默丢记录；备份和恢复说明随实现补齐。
- 长对话压缩后完整历史仍可查看；未开放会话列表、side chat 或文件/脚本执行能力。
