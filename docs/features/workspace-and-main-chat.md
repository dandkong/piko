# 工作区与主会话模型

状态：首个增量已实现；自动化检查覆盖持久化与恢复，真实模型长对话压缩及设备后台切换仍需使用验证。遵循 [产品约定](../PRODUCT.md) 和 [架构约定](../ARCHITECTURE.md)。

## 目标与范围

用户始终回到同一个主会话。后端工作区是助理长期使用的独立文件夹；聊天正文与模型上下文持久化。此次保留既有布局、键盘、滚动和流式交互。

包含 Workspace / Thread、消息与 Run 投影、唯一主会话、JSONL 与 SQLite 索引、Pi 上下文恢复、受控指导/技能发现和中断处理。随后已启用 Pi 的 read、write、edit、bash 四个内建工具，支持文件操作、技能正文读取/创建和脚本执行。side chat 预留类型与父会话关系，没有创建 API 或 UI；自动记忆、Activity 和后台任务尚未实现。

## 配置与初始化

- `PIKO_HOME`：默认 `~/.piko`，保存工作区与独立 state；`PIKO_WORKSPACE`：可单独指定工作区。均为绝对路径。
- 初次创建 `.agents/skills`、memory、projects、artifacts，以及 AGENTS.md、SOUL.md、USER.md、MEMORY.md 模板。再次启动保留用户文件；类型冲突和越界链接拒绝。
- 状态位于 `PIKO_HOME/state`，必须在工作区外。SQLite schema 当前为 1；未来版本数据库拒绝打开，不覆写或自动降级。
- 一个状态目录只允许一个后端进程。活进程锁拒绝第二个实例；确认进程不存在后可自动清理遗留锁。无效锁不会擅自移除。
- 模型/凭据沿用 Pi profile；资源、压缩、重试等参数由 Piko 适配器控制。

## 存储约定

| 存储 | 保存什么 |
| --- | --- |
| `state/piko.sqlite` | Workspace/Thread 身份与关系、Run 顺序/状态/游标/文件名、Pi session/leaf 检查点 |
| `state/runs/<run-id>.jsonl` | 版本 1 的 Run 头（输入、时间、重试来源）与 append-only 检查点（增量、事件、错误、终态） |
| `state/pi-sessions/<thread-id>.jsonl` | Pi SDK 原生 session、模型消息、压缩摘要与分支 |
| `workspace/` | 用户指导、技能、记忆和未来成果文件 |

SQLite 不保存消息或事件正文；客户端 Message 从 Run 日志投影，使用 `user-<run-id>` 和 `assistant-<run-id>` 稳定 ID。主 Thread UUID 同时是现有 API 的 sessionId，Pi session UUID 独立。

提交先创建并 fsync Run 头，再在事务中建立索引，之后才创建/调用模型。SQLite 保证一个工作区唯一 main、一个 Thread 只有一个活跃 Run。同 runId、同内容及重试来源返回已有记录，内容变化拒绝。重试必须引用同 Thread 的失败 Run 并使用同样输入，产生新 Run。

增量按最多 50 毫秒间隔合并保存，首段和终态立即保存；写入并 fsync 成功后更新索引和发布事件。强制终止最多丢失尚未保存的合并缓冲区或上游尚未接收的输出，不会把未保存内容当成成功结果。保存失败阻止后续执行，修复存储后重启恢复。

所有事件保留于 JSONL；内存续订窗口为最近 2,048 条，过期游标先读完整快照。首期仍全量加载可见历史；历史分页、大文件增量读取与日志压缩后续按规模引入。

## 主会话 API 与客户端

- `GET /api/main` 返回 `{ workspace, thread, sessionId }`，不同客户端共享同一主会话。
- 现有聊天、快照、续订、取消 API 保留；`POST /api/chat` 新增可选 retryOfRunId。
- 主会话删除暂不可用；任意客户端 UUID 不再自动创建会话。旧 ID 返回 409，要求刷新到主会话。
- 客户端启动从后端解析主会话，并清理旧 AsyncStorage sessionId；不再生成或持久保存独立聊天 ID。连接失败可重试发现。
- 服务端之前只有内存历史，此次不做旧进程历史导入，不能恢复已经因重启丢失的内容。

## Pi 资源

显式加载工作区 `.agents/skills` 和应用内建技能，用户同名技能优先并记录诊断。关闭默认全局、祖先指导、扩展、提示模板和主题发现，避免继承源码或个人 CLI 资源。

内建核心指导加工作区 AGENTS.md（8,000 字节），SOUL.md / USER.md / MEMORY.md 各 4,000 字节；超量截断并标注，每轮发送前重新读取。模型通过 read 按需读取完整技能，write/edit 创建或修改技能，通过 Bash 执行脚本；记忆文件可手动或按用户要求维护，自动提取与检索未实现。

启用 read、write、edit、bash 四个 Pi 内建工具，每轮资源刷新后保持启用。相对路径和命令 cwd 为助手工作区，执行权限为后端进程的本机权限；当前没有工作区沙箱或单独审批界面。全局/祖先扩展不自动启用。工具参数与结果写入 Pi 原生 JSONL，文本 SSE 契约不变；操作进度、工具日志查看和产物界面后续开发。

Pi 原生上下文压缩开启，保留完整业务历史；模型瞬时失败由 Pi 有限重试。用户主动重试与服务重启不自动重跑的语义仍由 Piko 管理。

## 崩溃恢复

1. 启动检查已索引文件，JSONL 领先时修复 SQLite 状态与游标；处理已写入但尚未入库的孤立提交。
2. 文件末尾半条 JSON 先保存 `.torn-<time>` 副本，再截掉残片；内部损坏、索引领先、文件缺失或未知所属 Thread 均拒绝继续，要求恢复一致备份。
3. 遗留 queued / running / cancelling Run 保存为 `failed + errorCode: interrupted`，保留部分输出并追加错误事件。不自动调用模型。
4. Pi 从数据库记录的 committed leaf 恢复。未提交尾部保留在原生文件的旧分支；对应中断输入/部分输出以历史说明加入新分支，避免把它当成新执行请求。
5. 新创建 header 在保存数据库指针前崩溃可以恢复；存在完整会话却没有可对应业务记录、session ID/leaf 不匹配或 Pi 文件损坏时不会默默开空会话。

Pi 写入、Piko JSONL 与 SQLite 没有跨文件事务；通过写入顺序、运行索引和已提交分支检查点恢复。状态目录不能在后端运行时人工编辑或删除。

## 备份与恢复

先停止 API，再一并复制整个 `PIKO_HOME`；自定义 PIKO_WORKSPACE 时同时备份该目录。保留 SQLite（包括仍存在的 WAL/SHM）、runs 与 pi-sessions，模型凭据仍属于独立 Pi profile。运行中的简单文件复制不作为一致备份。

恢复时停掉后端，使用同一批次备份恢复完整状态与工作区，并保留原工作区绝对路径。数据库以规范化路径辨识 Workspace，迁移到新路径的正式导入尚未实现，直接改路径会解析为另一个工作区。

缺失/损坏先保留现场并恢复一致备份；不要只删数据库、只删 Pi 文件或只回滚一部分日志。无效 backend.lock 需人工确认无进程后处理；普通已退出进程的锁由启动检测处理。

## 验证与后续

自动化验证覆盖模板幂等、冲突/路径、主会话唯一、多客户端发现、提交去重与并发、重启历史/稳定 ID、部分输出中断、重试来源、日志领先修复、孤立提交、尾部残片/内部损坏、未来 schema、模型检查点、压缩摘要、分支与资源隔离。现有 SSE、取消、流恢复、键盘测试继续保留。

新增工具检查覆盖四个工具注册、资源刷新后的激活、工作区文件读写/编辑、技能读取与创建，以及实际 Bash 脚本执行。真实模型的持续长对话、压缩触发和 Android 后台网络行为仍需使用验证。后续接入工具进度、产物查看、技能管理和访问边界；记忆、side chat 交互分别设计。
