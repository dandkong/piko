# 工作区与主会话模型

状态：源码使用 Durable 原生 SQLite，不维护 Piko 自建消息/Run 表；JSONL 副本核验及线上停机迁移已完成，见 [SQLite 存储](sqlite-storage.md)。架构见 [ARCHITECTURE](../ARCHITECTURE.md)，模型与运行时见 [Durable 配置](durable-runtime.md)。

## 范围与初始化

一个 PIKO_HOME、一个长期工作区、一个 Harness/root 主会话；后台委派使用同一 Harness 的持久化子会话，不增加展示，见 [后台子 Agent](background-subagents.md)。[任务与执行记录](tasks.md) 已在同一 Harness 接入，Tasks 按进行中/已归档展示任务与执行记录，并支持归档/恢复；归档不等于单次执行完成。每日/长期记忆整理已接入；[旁聊](side-chats.md) 已复用同一 Harness 接入独立用户聊天，不参与主会话的记忆提取。全局产物管理尚未实现。

默认 PIKO_HOME 为 ~/.piko，仅部署环境 PIKO_WORKSPACE 可指定绝对工作区；加载见 [应用配置](application-config.md)。初始化只补缺失配置和模板，保留用户内容。state 在工作区外，通过后端锁限制单写进程。已有主会话 cwd 与配置不同则拒绝启动，恢复原路径或使用新 PIKO_HOME。

| 存储 | 内容 |
| --- | --- |
| config/piko.json、.env | 应用配置与可选覆盖 |
| config/piko.json、models.json | 统一的非敏感 Agent/通道/工具行为，以及独立模型目录；不再生成 settings.json |
| config/.env 与进程环境 | 部署参数与敏感凭据，不覆盖 JSON 行为 |
| state/durable/ | session.sqlite（及运行期 WAL/SHM），唯一持久会话与执行状态来源 |
| state/tmp/ | 工具溢出与可清理临时文件 |
| 当前进程内存 | 流式消息、输出合并、Session 中待挂接的后台回传、TG 投递身份 |
| workspace/ | AGENTS.md、MEMORY.md、memory/ 每日记忆、技能与工作成果 |

没有 Piko 身份表、执行表、输入哈希、正文副本或永久 SSE 日志。停止去重和中断提示使用原生文档，不重复保存任务状态。更旧的 Piko 自建 SQLite 和 durable-sessions 不作为当前来源；本次仅提供当前 Durable JSONL 到原生 SQLite 的显式迁移。

## 展示与上下文

展示从原生原始 entries 正序投影用户/助手文字，保留 reset、上下文编辑和压缩前历史。气泡 ID 为 pi-<entry ID>，时间来自原生消息。工具、思考、隐藏 entry 和压缩摘要不显示；不预留尚无写入端的被动结果展示分支。

Web/RN 的首次快照与后续 SSE 快照只传最近 50 条可见已保存消息，另附当前流式消息与未应用输入。`GET /api/chat/history?before=<entry ID>` 向前读取至多 50 条，`nextBefore` 表示还可向前翻页；游标基于不可变 entry ID，新增消息不会移动旧页边界。每页与状态在原生 commit 线上读取；提交绑定从原生 submission 初始化并随 commit 更新，不新建正文或永久索引。

客户端向上滚到顶部附近自动加载更早消息，可手动点击加载或失败重试；加载时保留阅读位置。最近快照覆盖所含范围及临时输入，不清掉已经翻出的更早记录。失联期间若增长超过最近窗口、与客户端记录无交集，则重置到最新页，避免掩盖中间缺口；旧请求的分页响应不混入新窗口。客户端仅加载访问过的页，但目前不会自动淘汰已加载页；服务端运行时仍保留完整原生历史用于事件恢复，启动与运行时内存不因此变为常量。

每条用户消息从原生 submission.entry 获取 requestId，不额外写 piko.input。助手消息独立展示，不累计整轮回答、不强行配对。当前流式消息采用临时 ID，保存后原位替换；原生 inbox 里的未应用输入临时显示，撤回后消失。模型上下文和压缩由 Durable 处理，UI 不读取压缩后的 context 代替历史。

## 执行、停止与传输

POST /api/chat 接收 {requestId,message}，返回原生提交回执。RN 新请求生成 UUID，网络重试保持该 ID；TG 使用 telegram:<botId>:<chatId>:<messageId>。同 ID 返回原提交；新意图使用新 ID，不再做哈希冲突或 retryOfRunId 关联校验。用户主动重试生成新 ID，连接恢复只观察、不自动重发。

输入、停止与维护预留由 DurableChatSession 的单一接纳线协调；ConversationStore 只负责文本校验、输出合并与观察，不重复维护锁或后台回传缓存。普通输入使用 whenBusy=steer 与 steeringMode=all，运行期间仍可接纳，在原生边界全部应用；不强行打断模型或工具。模型/思考选择及手动压缩占用空闲边界，期间普通输入立即拒绝；停止可取消压缩。

GET /api/chat/events 是持续会话 SSE，与每条输入提交分开。每次连接先发送最近一页的 authoritative snapshot，再继续实时更新；不使用事件游标和重放缓存，不补齐断线期间的中间流式事件。首次快照与实时订阅仍衔接在同一发布线上，防止漏掉期间的变化。消息更新最多 50ms 合并，15 秒心跳，客户端 30 秒无数据重连并有限退避。断线、页面卸载和退后台均只退订，服务端继续工作。

POST /api/chat/stop 以独立 requestId 停止 conversation 和待应用输入。原生 piko.stop 文档记录当时的 task ID，重复请求只取消原目标，不影响之后的新工作。执行失败也结算和撤回剩余输入；未落入原生用户 entries 的输入不进入最终历史。提交状态使用原生 queued/placed/done/unanswered，不另存 Piko 终态。

RN 在前台持续观察两通道变化，原生快照加未确认的本地输入构成列表；过期 HTTP 刷新不会覆盖较新的观察结果。TG 按助手消息维护投递，网络发送不阻塞接纳或执行。接口见 [架构说明](../ARCHITECTURE.md)，通道边界见 [Telegram 通道](telegram-channel.md)。

## 资源与工具

核心指导随应用发布，工作区保存由用户定制的指导与记忆文件。注入时标注来源路径和 `role`，职责如下：

| 文件 | role | 职责 |
| --- | --- | --- |
| 应用 `core.md` | core | 应用运行规则、工具使用与结果真实性，不固定助手名字或语气 |
| 工作区 `AGENTS.md` | work_guidance | 如何表达和做事：助手名字、语气、回复偏好、工作方法、文件组织和交付约定；默认名字 Piko 在此定义 |
| 工作区 `MEMORY.md` | memory | 需要记住的事实：用户资料、环境事实、个人偏好、项目决定与长期结论；不推测未提供的信息，不作为聊天记录或操作授权；不复制 AGENTS.md 中已有的助手行为规则 |
| 工作区 `memory/YYYY-MM-DD.md` | memory（按需读取） | 每日记忆：当天有延续价值的讨论、已确认的决定、做过的事、用户近况与未完线索；不自动注入 |

助手如何表达和工作的长期约定放在 AGENTS.md；用户资料、环境事实、个人偏好和其他长期结论放在 MEMORY.md；每日讨论、决定、进展和未完线索放在 `memory/YYYY-MM-DD.md`。助手行为规则在 AGENTS.md 与 MEMORY.md 之间只保留一个事实源；各文件内部用 Markdown 小节组织，无需按身份、用户资料等再次拆文件。

`role` 是资源用途标注，不是独立的模型消息权限层级，也不构成安全隔离。实际能力与文件访问边界必须由运行时实现。

core.md、工作区 AGENTS.md 和 MEMORY.md 均完整读取，不设应用层字符/字节上限，也不静默截断；后台任务自己的 items/<id>/MEMORY.md 同样完整读取。实际可用上下文仍受所选模型窗口约束；静态文件内容过大时，底层可能压缩聊天历史，但如果总请求仍超过模型窗口，也可能由模型服务拒绝。应用不会为规避窗口错误而静默丢弃文件尾部。每次模型请求重新加载指导和技能索引，技能正文通过 read 按需读取；每日记忆不自动注入，相关时由助手通过工作区 read/search 查阅。初始化只补缺失的 AGENTS.md、MEMORY.md，模板升级不覆盖已有用户文件。其他旧指导文件不再初始化或加载，也不会自动删除或搬移其内容。

### 每日与长期记忆整理

主会话结束并闲置 30 分钟后，运行一个独立 Durable 后台记忆整理 task。它只选取上次游标之后新增的主会话原始用户/助手文本，不处理内部子 Agent 回报、工具日志，也不回填启用前的历史。没有可读新增文本时只推进游标，不调用模型。整理只由后台闲置调度触发，不向主 Agent 提供手动触发工具；不会完成后向主聊天发回报。

一个 整理 task 启动专用子会话，只配置 `read`、`write`、`edit` 三个工具，由 整理者 读取当前文件并直接编辑；不提供 bash。一次整理同时维护两类记忆；为了使用文件工具，模型可能经历多个工具调用轮次。

- `memory/YYYY-MM-DD.md` 追加有延续价值的讨论/想法、已确认决定与变化、做过的任务及结果、用户主动分享的近况和未完线索；允许短期细节，不写逐条来源 ID。
- `MEMORY.md` 只保留仍有效、跨会话值得携带的用户资料、环境事实、个人偏好和长期结论；AGENTS.md 已表达的助手行为/工作流规则不再复制到 MEMORY.md。若发现同义重复，只清除重复规则，不删同主题下独立的用户事实；不将每日记忆摘要直接照搬成事实，并可按明确纠正更新过时内容。

游标、活动 task 和重试状态存于 Durable 文档，不写进记忆正文。整理者读取 AGENTS.md 作为只读去重参考，并被提示只改 `MEMORY.md` 和本批对应的日期文件；但这只是行为约定，不是权限沙箱：三个工具使用后端本机权限，`write`/`edit` 仍可指向任意路径。文件写入与 Durable 游标不在同一事务；task 中断时不自动续跑，游标不推进，后续新的整理会先读取当前文件再处理原范围。程序不做文件哈希冲突检测、回滚或写入结果独立校验；若写文件后中断，避免重复依赖整理者的判断。这比候选 JSON + 程序提交更简单，但并发改写和模型未正确落盘时的保护更弱。

技能来源为工作区 `.agents/skills` 与应用内建技能；同名时工作区版本优先，同名覆盖有诊断。`PIKO_HOME/skills` 不创建也不读取。不继承个人 Pi CLI、祖先指导或全局扩展。模型配置独立于 Pi CLI；Durable Extension 只由 Piko 内建代码注册，用户 skill 不增加运行时工具。

read/write/edit/bash 保持启用，相对路径默认工作区，本机 Shell 执行命令。`WorkspaceExecutionEnv` 除进程环境外，只将显式白名单的用户技能变量从 `PIKO_HOME/config/.env` 传给 Shell，不整体导出应用凭据。cwd 不是沙箱；目前没有操作审批 UI。durable 的 read 已能读取图片，附件存储与上传接口见 [附件与图片读取](attachments.md)，RN 选图仍是占位。记忆整理已实现；专门的记忆浏览、检索和版本管理 UI 尚未实现。

## 中断与损坏恢复

1. 启动取得锁、打开固定 state/durable/session.sqlite，校验原生存储、root 与工作区关联。
2. 损坏数据库拒绝继续；目录含旧 JSONL，或非空目录缺少 session.sqlite，明确报错，不初始化空会话或静默回退。SQLite 处理 WAL 事务恢复。
3. 启用调度前撤回遗留输入并取消不确定执行；仅保留已完成子任务的 Reporter report 阶段，随后 resume 回传结果，不自动重跑模型和工具。
4. 有遗留生成或输入时写原生 piko.recovery 中断提示和隐藏上下文说明，不复制输入、不调用模型；下一次接纳清除提示。
5. 已保存历史继续展示；尚未保存的文字不保证恢复。恢复不回滚工具的外部副作用。

## 开发数据与备份

当前原生 JSONL 可按 [迁移说明](sqlite-storage.md) 离线导入独立目录并停机切换，不自动迁移更旧的 Piko 自建数据库。配置、模型凭据、工作区文件和技能不随存储切换删除。重置须明确确认并先备份、停止后端，不可只删除数据库主文件而保留 WAL。

备份停止 API 后复制整个 PIKO_HOME 和单独指定的工作区；SQLite 目录成套保存，恢复保留原工作区绝对路径。迁移前 JSONL 和历史备份仍含原始隐私内容，切换不等于清除它们。
