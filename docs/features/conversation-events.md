# 会话事件与实时活动

会话和执行状态仍以 Durable 原生 SQLite 为事实源。本章描述进程内事件投影、客户端协议及 Telegram 呈现，不引入消息副本、持久事件日志或可靠 outbox。

## 分层与职责

```text
Durable observeConversation / observeCommits / LiveDoc / 原始 entries
    ↓ server/runtime/ConversationView
Piko SessionEvent（运行时事实）
    ├─ ConversationStore → 客户端 StreamEvent → SSE → Web / iOS / Android
    └─ observeRuntime → TelegramConversationOutput → TelegramReply
```

- `ConversationView` 是 SDK 适配边界：从结构化会话状态投影用户/助手文字、工具开始/结束、执行开始/结束、已应用用户输入、压缩和实时活动；外部 Piko `SessionEvent` 与 RN/TG 协议保持稳定。
- `SessionEvent` 在 `server/runtime/types.ts` 定义，不包含传输快照和通道呈现指令。`invalidated` 只表示需要重新读取状态，不对外发送。
- `ConversationStore` 对客户端只投影五类事件，正文更新最多合并 50ms，状态失效时重读原生快照；完整运行时事实只通过 `observeRuntime` 提供给 TG。
- 客户端与 TG 都不拥有执行生命周期。断线或关闭观察只退订；输入、停止、维护与内部报告仍经过原有接纳线。

## 客户端协议

| type | 内容与语义 |
| --- | --- |
| `snapshot` | 最近消息窗口、busy、activity、提交回执、压缩和其他会话状态；首次连接/重连的恢复起点 |
| `message` | 一条用户/助手消息的当前正文、final 标志，以及流式身份替换的 previousId |
| `activity` | 当前助手活动的完整替换值，而非开始/结束增量 |
| `error` | 用户可见错误提示 |
| `deleted` | 会话已删除，客户端停止观察并清空对应状态 |

契约类型在 `shared/chat.ts`；`shared/conversation-events.ts` 集中验证 wire payload。验证器表用类型检查覆盖全部公开事件种类；已知事件格式不正确会使当前流失败并按既有逻辑重连，不能静默丢掉。`shared/sse.ts` 只处理帧编码/拆分，不再自行维护另一套事件种类。

运行时的工具参数摘要、压缩通知和内部失效信号不进入客户端协议。SSE 不保存游标或重放日志。新连接先发送最新快照，再继续更新；连接和前后台变化不重投用户输入。

## 实时活动

`ConversationActivity` 是原生状态的临时展示投影：

- `idle`：当前没有忙碌工作。
- `thinking`：整轮执行开始时的占位活动。
- `replying`：最近一次观察到的活动是正文输出。
- `tool`：最近一次观察到的活动是工具开始，附工具名，不附参数、路径或输出。

活动采用“最近事件覆盖”而不是精确运行阶段：工具开始或正文输出更新标签；工具结束、单条消息结束、思考块或重试不使标签回退。标签一直保持到下一次明确活动覆盖，原生 `pi.live.run` 消失（Piko 投影的执行结束边界）才清空。这里的整轮不是工具循环中间的 `turn_end`。并行工具也只显示最后启动的标签，不在完成时切回其他工具。

`conversation-activity.ts` 负责从 Durable `LiveState` 投影活动；同一进程内 HTTP/SSE 快照保留本轮最近一次已知活动，不因工具完成或正文结束而回退。初次观察或原生状态恢复时，可以从 `pi.live` 的工具 slots 和 generation 恢复明确的当前工具/正文；无可恢复线索时从思考占位开始。没有另外持久化活动状态，跨后端重启不承诺恢复已经结束的上一项活动。

各端头像下方现有状态栏使用同一映射：如“搜索网页”“执行命令”“读取文件”“正在回复”；没有中文映射的工具统一显示“调用工具”。加载、上传、停止和重连状态仍优先。客户端不维护活跃工具 Map，不通过消息 ID 前缀推断头像活动，也不新增聊天气泡。

## Telegram 有序呈现

`TelegramConversationOutput` 用一个串行呈现队列处理主会话正文、工具、执行边界与压缩通知：

- 连续工具开始聚合在同一条临时纯文本消息；助手正文、已应用用户输入、新执行和压缩开始会结束当前工具段。
- 正文按原生助手消息独立投递，流式 Rich Markdown、800ms 合并及最终即时刷新保持不变。工具开始前先冲刷其之前的正文，不由另一条工具发送队列抢先发出。
- 原生执行结束先冲刷最后正文，再删除本轮全部临时工具段。没有单独的“清空工具”或“工具分段”事件。
- 执行结束事件携带对应原生 submissions 的回执，失败/停止反馈不通过稍后的 latest 快照猜测上一轮结果。TG `/stop` 自带反馈，因此在呈现队列中抑制该轮重复停止提示；App 停止仍可向 TG 通知。
- 自动 threshold/overflow 压缩不发送通知；手动 manual 压缩保留开始/结束通知，并保持已验证私聊地址的通知边界。
- 订阅以当前快照建立已保存历史基线，不重放历史；订阅时的实时回复可继续呈现。主会话回复不按输入来源过滤，用户输入不回显，旁聊/子会话原文不直接投递。

后台回报提示仍只是进程内的通道唤醒提示；它不包含需要直接发布的子会话正文，也不是执行状态。所有最终输出仍由主会话助手事件驱动。

网络失败不回滚执行或重跑模型。投递身份和发送进度只在内存，重启可能漏发、网络超时重试可能重复；本机制不承诺可靠补发或恰好一次投递。

## 验证边界

临时隔离脚本使用真实 Durable runtime、SQLite、faux 模型和模拟 Telegram transport，覆盖原生工具/正文到 SSE 编解码及活动标签、并行工具最近标签保持、工具中途重新订阅、TG 正文与工具交错顺序、最终正文后清理、输入去重、引用输入、停止及自动压缩静默。共享 Chromium 使用隔离后端和正式 Web bundle 验证头像工具标签、执行中刷新恢复、回复标签及结束清空。

真实模型供应商、真实 Telegram 网络和 iOS/Android 真机行为仍需实际使用核验。
