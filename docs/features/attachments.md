# 附件与图片读取

状态：服务端支持接收附件和助手发送文件；Web 聊天支持选择文件或在输入框粘贴剪贴板提供的文件和截图，iOS/Android 原生文件选择和图片粘贴尚未接入。聊天中每个附件独占一行，文件名下方可有消息正文；不提供图片缩略图。音频文件可在支持的客户端内播放预览。

## 统一附件存储

用户上传、Telegram 下载及助手发送的文件都保存在同一目录，不在工作区内：

```text
PIKO_HOME/state/attachments/<UUID>/<原文件名>  # 新接收的用户文件
PIKO_HOME/state/attachments/<UUID>             # 助手发送的快照
```

- 接收任意文件：图片、PDF、Office 文档、音视频等，模型自己决定如何检查
- 每次上传或下载均使用独立 UUID 目录，目录内保留安全化的原文件名；同名文件不会互相覆盖，剪贴板文件名无需加唯一前缀。无文件名时按嗅探类型或客户端 MIME 生成默认名；路径永远不由客户端提供。此前保存在附件目录根部的用户文件和历史链接仍可读取。
- 单文件上限 20 MiB；图片按字节嗅探类型，其他类型通过 `mime-types` 根据后缀推断；无后缀或未知类型历史记录按普通二进制处理
- 接收文件和助手发送的快照均不自动过期；手动清理文件会使对应的历史附件失效
- 附件属于运行时数据，不参与工作区备份语义；`PIKO_HOME` 备份时一并复制

实现见 `server/attachments.ts`；旧 `state/sent-attachments/` 在启动时安全迁移到统一目录，保留已有助手附件 ID 和历史链接。

## 助手发送文件

- 主聊和未归档旁聊的助手可以调用 `send_attachment(path)`，参数是本机绝对路径；每次发送一个文件，不带文字参数。助手仍可另发普通文本。后台子 Agent 和任务不能直接发送，可将生成文件的路径交给所属聊天的助手。
- 只接受非空、最大 20 MiB 的普通文件，不跟随路径最后一段符号链接。发送时把文件复制为 `PIKO_HOME/state/attachments/<UUID>` 下的独立快照，原文件保持不变；原始安全化文件名保存在会话记录中，用于展示和下载。相同文件名也不会互相覆盖。
- 助手发送的快照暂不自动清理；删除旁聊也不会删除快照，备份 `PIKO_HOME` 时应一并保护。会话记录使用 Durable `piko.chat-attachment` entry 保存快照身份、文件名和 MIME 类型等元数据，实时投影和历史恢复共用同一记录。MIME 使用 `mime-types` 按文件名后缀查询，未知类型回退 `application/octet-stream`。用户上传和历史恢复也使用同一查询库，不改变用户消息的存储结构。
- 主聊附件尽力同步到 Telegram，使用 `sendDocument` 发送原名文件；旁聊附件不自动投递 Telegram。会话记录先于 Telegram 投递，发送失败不会回滚会话，也不自动重试或补发；超时结果可能不确定。

## 展示与音频预览

- 用户和助手附件均逐行显示文件名；点击文件区域打开预览，点击行末独立按钮下载原文件。支持的文本和 Markdown、UTF-8 解码及 1 MiB 上限与 Artifacts 共用；不支持或过大的文件可下载。文件名可用宽度随气泡缩小，超长省略。
- 对于支持的音频，点击文件区域播放或暂停，左侧图标显示播放状态，行末下载按钮仍然可用；不展示或持久化音频时长，也不提供单独的语音发送工具。播放完成后再次点击从头播放，同一时刻只播放一个文件。
- 当前识别 MP3、M4A、OGG、WAV，实际可播放的格式和编码取决于浏览器或设备。Web 对浏览器声明不支持的格式按其他文件处理；播放失败会提示。音频仅按需加载；服务端校验格式后提供可供播放的响应和字节范围请求，不内置 TTS、转码或自动转写。文件下载入口与 Artifacts 共用客户端动作，原生设备的实际保存行为仍需验证。

## 入口

| 来源 | 获取字节 | 说明 |
| --- | --- | --- |
| Telegram | photo 取最大尺寸；document / video / audio / voice 全部接收；`getFile` 后下载到共享存储 | 相册不合并，每条消息分别处理；caption 作为文字 |
| App Web | 聊天中选择文件，或在输入框粘贴浏览器提供的文件/截图后调用 `POST /api/attachments`，请求体是原始字节 | 支持的粘贴内容取决于浏览器和复制来源；普通文本正常粘贴，附件需用户自行发送。上传期间新粘贴的文件排队，失败保留待重试。原生客户端尚不支持选取文件或粘贴图片 |

`POST /api/chat` 接受可选的 `attachmentIds`（最多 4 个）。服务端解析为绝对路径后交给运行时，通道本身不拼提示词。

## 模型看到什么

只有一个注入点 `server/chat/input.ts` 的 `attachmentPrompt`：

```text
<attached>
~/.piko/state/attachments/<uuid>/photo.jpg
</attached>
用户文字
```

两个通道因此得到完全相同的表示。UI 与 TG `/recent` 在投影时把这段去掉，只显示 `📎 附件` 或后续文字；模型仍看到完整路径。模型用 `read` 打开路径：

- `read` 返回文本，或一个 `ImageContent` 块；图片由 Photon 处理器做方向校正、转码和缩放
- 其他类型不做预处理：模型可以 `read` 文本类文件，或用 bash 的 `file`、`head`、`unzip -l`、`ffprobe` 等自行探测；Piko 不在工具层做类型分派
- 当前模型没有 `image` 输入能力时，上游给出占位文本和诊断，Piko 不静默降级成“看过图了”
- 附件内容进入上下文后占用 token；单条消息最多 4 个，建议按需发送
